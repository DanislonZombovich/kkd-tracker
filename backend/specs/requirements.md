# Requirements Specification: Модуль ККД (Backend Java)

## 1. Назначение и цели
Сервис контроля качества данных (ККД) по целям и ключевым результатам сотрудников предназначен для автоматизированной проверки корректности целеполагания в блоке B2B.

## 2. Функциональные требования
1. **Хранение данных в PostgreSQL:**
   - Подразделения с многоуровневой иерархией (`parent_id`, `depth`).
   - Цели (Goal) со статусом (`active`, `closed`, `cancelled`), уровнем каскада (`block`, `hq`, `unit`), ответственным лицом и сроком.
   - Ключевые результаты (KeyResult) с весами, целевыми и фактическими значениями, датой последнего обновления факта.
   - Журнал еженедельных прогонов (`kkd_runs`) и реестр обнаруженных дефектов (`kkd_issues`).
2. **Изолированный движок бизнес-правил (`KkdRuleEngine`):**
   - Правила вынесены в отдельный слой, независимый от контроллеров и БД.
   - Реализовано 6 правил (включая критические и каскадные):
     - `GOAL_NO_OWNER` (critical) — цель без ответственного;
     - `GOAL_NO_KR` (critical) — активная цель без ключевых результатов;
     - `KR_WEIGHTS_SUM` (major) — сумма весов КР ≠ 100%;
     - `CASCADE_NO_PARENT` (major) — некорневая цель без связи с целью вышестоящего уровня;
     - `KR_NO_TARGET` (major) — КР без целевого значения;
     - `KR_STALE_PROGRESS` (minor) — факт КР не обновлялся более 45 дней.
3. **Иерархический расчёт метрик подразделения:**
   - Метрики подразделения рассчитываются кумулятивно: по целям самого подразделения и всех его дочерних подразделений (`descendants_or_self`).
   - Основные метрики:
     - `clean_goals_share` (%): доля активных целей без единого дефекта;
     - `cascade_coverage` (%): покрытие каскадом некорневых целей;
     - `issues_total` (шт.): суммарное число проблем;
     - `critical_issues` (шт.): число критических дефектов.
4. **Сравнение прогонов и расчёт дельты:**
   - Сопоставление с предшествующим успешным прогоном.
   - Дефект считается тем же самым при совпадении `rule_code` и `object_id`.
   - Подсчёт дельты: `new` (новые), `persisting` (сохраняющиеся), `resolved` (исправленные).
   - Для первого прогона (`RUN-001`) значения `previous`, `delta`, `trend` и счётчики дельты строго равны `null` (не 0).
5. **REST API:**
   - `GET /api/meta` — справочники подразделений (null `parent_id` для корня), правил, важностей, уровней целей, метрик и статусов дельты;
   - `GET /api/runs` — история прогонов с пагинацией;
   - `GET /api/kkd/summary?run_id=&unit_id=` — агрегированная сводка с дельтой, трендом, `issues_by_severity` и `issues_by_rule`;
   - `GET /api/kkd/issues?run_id=&unit_id=&rule_code=&severity=&delta_status=&q=&sort=&limit=&offset` — пагинированный список проблем с полнотекстовым поиском `q`, сортировкой и фильтрацией (по умолчанию отдаются только активные дефекты `new`/`persisting`, а `resolved` — только при явном фильтре `delta_status=resolved`);
   - `GET /api/kkd/issues/{id}?run_id=` — карточка проблемы с историей по прогонам (с честным отображением `null` для неуспешных прогонов).

## 3. Критерии приёмки (Acceptance Criteria)
- Все 33 теста (JUnit 5) успешно проходят: проверка всех 6 правил на граничных условиях, расчёт метрик с иерархией, расчёт дельты, фильтрация и поиск проблем, честная история прогонов.
- Накат, откат и повторный накат миграций Liquibase выполняются без ошибок (включая каскадное удаление связей и очистку таблиц).
- Единый формат ошибок: `{"error": {"code": "...", "message": "..."}}`.
- Полная работоспособность в Docker Compose.
